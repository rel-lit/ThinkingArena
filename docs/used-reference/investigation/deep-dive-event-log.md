## 问题 1：事件 id / parent_id 生成方案选型

### 1.1 pi 的实际做法（事实核查）

直接读取 pi 当前源码（commit `2fd3868`，2026-07-20，`packages/coding-agent/src/core/session-manager.ts`，[永久链接](https://github.com/earendil-works/pi/blob/2fd3868401f0fe79496f3df731b20348ba57538a/packages/coding-agent/src/core/session-manager.ts)）：

pi 采用**两层 id 方案**：

1. **会话 id = UUID v7**：`createSessionId()` 调用 `uuidv7()`（来自 `@earendil-works/pi-ai`），用于会话文件命名（`${timestamp}_${sessionId}.jsonl`）与跨文件引用（`parentSession` 字段）。
2. **条目 id = 8 位十六进制短随机串 + 碰撞检查**：
   ```typescript
   function generateId(byId: { has(id: string): boolean }): string {
     for (let i = 0; i < 100; i++) {
       const id = randomUUID().slice(0, 8);   // 取 UUID v4 前 8 位 hex
       if (!byId.has(id)) return id;           // 对内存索引做碰撞检查
     }
     return randomUUID();                      // 100 次碰撞兜底用完整 UUID
   }
   ```
   所有条目类型（message / compaction / branch_summary / label / custom…）统一经 `generateId(this.byId)` 分配，`parentId: string | null` 指向父条目；`CompactionEntry.firstKeptEntryId`、`LabelEntry.targetId`、`BranchSummaryEntry.fromId` 均以该短 id 引用任意历史条目——即 pi 自身就是"id 引用任意历史事件 + 单文件多分支共存"的已验证先例。

**与本仓既有调研的差异（勘误）**：`docs/used-reference/investigation/pi-agent-investigation.md` §2.3/§6 描述的是 `uuid`/`parentUuid` 字段与完整 UUID——那是 pi 会话格式 v1 时代的写法；当前 v3 格式字段名为 `id`/`parentId`，且条目 id 实为 8 位短串。以源码为准。

### 1.2 候选方案对照

| 维度 | UUID v4 | UUID v7 | ULID | 文件内单调序号 | 内容 hash |
|---|---|---|---|---|---|
| 单写者下唯一性保证（D23） | 随机（概率性） | 时间+随机 | 时间+随机 | **计数器（确定性）** | 内容决定 |
| 同文件多分支共存（fork，D32） | 无冲突 | 无冲突 | 无冲突 | 无冲突（序号全局递增，与分支无关） | **重跑重放同内容即撞 id（见 1.3-④）** |
| id 自带顺序信息 | 无 | 有（毫秒级） | 有（字典序） | **有（id 序 = 文件序 = 追加序）** | 无 |
| 可读性（导演直接读 JSONL） | 差（36 字符） | 差（36 字符） | 中（26 字符） | **好（如 `e0001234`，8 字符）** | 差（64 字符 hex） |
| 行长开销（id + parent_id 两字段） | 72+ 字符 | 72+ 字符 | 52+ 字符 | **~18 字符** | 128+ 字符 |
| 跨局引用无歧义（D24 manifest 族谱） | 是 | 是 | 是 | 否（需配 run id 组成二元组） | 是 |
| pi 先例 | （会话 id 用 v7） | 会话 id 采用 | — | — | — |

### 1.3 逐项分析

**① 单写者使随机方案的核心价值落空。** UUID/ULID 的存在理由是无协调分布式唯一；D23（一局一进程单写者）下，事件由 EventLog 服务串行 append（D1/D35 唯一写者表），一个进程内计数器即提供**确定性**唯一，连 pi 的碰撞检查循环都可以省掉。随机方案在此场景只剩缺点：无顺序信息、占行宽。

**② parent_id 引用任意历史事件 + fork 共存：所有方案均满足，但序号方案额外受益。** 同版本内分叉后，新分支事件 append 在文件尾部（旧分支封存不再增长，§2.4-3 的 leaf 纪律），因此**全局（非分支内）单调序号的 id 序恒等于文件物理序**——导演肉眼即可判断事件先后，`grep` 定位后相邻行即上下文。若采用"分支内单调序号"（`branch:seq`），id 序与文件序在多分支后不再一致，调试体验反而下降；故序号应取**文件内全局序号**，不分支计数。

**③ 重放确定性：id 不参与 reduce，且这一点必须写进契约。** 五个方案都可以做到"id 不进 reduce"，但内容 hash 方案天然把 id 与载荷耦合，是最危险的一个：一旦有人利用"id = hash(内容)"做去重或完整性校验，id 就实质进入了重建逻辑。其余方案 id 是纯结构元数据，reduce 无视它即可。

**④ 内容 hash 被 D36 直接否决。** 崩溃恢复语义（D12/D36）：在飞节点作废、恢复后**重跑该节点并重新落盘**——重跑产生的事件与崩溃前孤儿事件类型、载荷完全相同（同一节点、同一迭代、同一参数），内容 hash 会得到**相同 id**，append-only 树中出现重复 id，索引与 parent 引用全部歧义。除非把墙钟时间戳纳入 hash——但那样 id 不再由内容决定，方案失去存在意义。排除。

**⑤ 与节点执行标识（D36）的关系：必须独立，不可合并。** 两者语义域不同：事件 id 标识"这一条落盘记录"（树节点），执行标识（节点 id, 迭代计数）标识"产生它的那次节点执行"。一对多（一次执行落多条事件：turn_start/speech/cost/node_end…）且生命周期规则不同——崩溃重跑时执行标识**复用**（同节点同迭代，用于识别并跳过孤儿事件），事件 id 必须**全新**。合并会同时破坏两个语义。这与架构 §3.3"调度进度以（节点，迭代计数）元组表达"一致：调度进度键就是执行标识，与事件 id 无关。

**⑥ UUID v7 的正确位置是 run id，不是事件 id。** D24 要求 run 目录命名含标识、manifest 记录跨局族谱指针；跨局引用场景没有"单写者"红利，时间有序的 UUID v7（pi 会话 id 同款选择）天然适合：目录按字典序即按时间排序、全局唯一无需登记。事件 id 只在局内被引用（parent_id、manifest 族谱中的"源事件 id"均与 run 目录成对出现），文件内序号 + run id 二元组即全局无歧义。

### 1.4 推荐

**两层方案（对齐 pi 的已验证结构，并将事件 id 从 pi 的短随机改为单调序号）：**

- **run id = UUID v7**：用于 run 目录命名、`run_started` 事件、manifest 族谱指针。
- **事件 id = 文件内全局零填充单调序号**：形如 `e0000001`（前缀 `e` + 7 位零填充数字，千万级事件内定宽、字典序 = 数值序）。由 EventLog 在 append/串行提交时分配；恢复时从最后一条事件（或最近快照条目携带的计数）续号。
- **parent_id = 同格式字符串或 `null`**（首条事件）。
- **节点执行标识 = 独立字段** `{ node: string, iter: number }`，与事件 id 无关（D36 原义）。

相对 pi 短随机的偏离理由：pi 需要短随机是因为它的条目可被复制进新会话文件（`createBranchedSession`/`forkFrom` 保留原 id），跨文件同 id 是特性；ThinkingArena 跨版本分叉是"新局新文件、旧局封存只读"（D21/§2.4-2），事件不跨文件迁移，单调序号无此顾虑，且换来 id 序 = 文件序的调试红利。

### 1.5 对架构/契约的影响

1. **事件契约 `id`/`parent_id` 字段类型应为 `string`（非 number）**：零填充序号是字符串；保留字符串类型也为未来改 UUID 留退路（契约不炸）。建议格式校验 `^e\d{7,}$`。
2. **事件契约须显式声明：`id`、`parent_id`、`ts` 为结构元数据，不参与 reduce**；reduce 的输入语义仅为 `type` + 载荷字段。这是"重放确定性"的契约化落点。
3. **接口 §4.3 `append(event)` 的入参应为"无 id 草稿"**，id/parent_id 由 EventLog 分配（写者不自带 id）——否则 D35 的多个写者各自造 id，唯一性与序号连续性都无法保证。Schema 阶段需据此定义 `EventDraft`（无 id）与 `Event`（有 id）两个类型。
4. **TCAS 批协议（D9）的取号时机**：批内缓冲事件的 id 必须在**批结束串行提交时**分配，而非组件发射进缓冲时——否则缓冲期取号会使 id 序偏离最终落盘序，破坏"id 序 = 文件序"不变量。
5. **节点执行标识保持独立字段**（D36 不变），禁止 Schema 阶段将其与事件 id 合并或互相派生。
6. **快照内联条目（D11）同属事件流条目，同样分配事件 id 与 parent_id**，其载荷中可携带"截至本快照已分配的最大序号"供崩溃恢复后续号（实现细节，供 Schema/实现参考）。
7. **D24 manifest 族谱指针的"源事件 id"** 应记录为 `(源 run id, 源事件 id)` 二元组——文件内序号单独不具备跨局唯一性。

## 问题 2：快照频率数值

### 2.1 实测方法

临时脚本 `task/tmp/replay-bench.mjs`（Node v24.12.0，Windows，本机实测；生成数据文件已删除，脚本保留可复现）。方法：

- 按 D35 事件族生成**合成 Script JSONL**：node_start/end、turn_start/end、speech（~150–450B 正文）、monologue（~2–8KB thinking 全文，D31 要求）、cost、prompt_hash、bb_set、director_intervention、dice、milestone，确定性伪随机混合，平均 **~575 B/事件**（含 id/parent_id/ts/node_exec 信封）。
- 重放 = 逐行 `JSON.parse` + 纯函数 `reduce`（黑板键值、Agent 生命周期表、（节点，迭代）进度表、成本账本累计——即 D22 定义的"事件流内状态"四段）。
- 两种读取路径各测 5 次取中位：A) `readFileSync` + `split('\n')`；B) 流式 `readline`（大文件的真实实现路径）。

### 2.2 实测数据

| 指标 | 1 万事件 | 10 万事件 |
|---|---|---|
| 文件体积 | 5.42 MB（569 B/事件） | 54.84 MB（575 B/事件） |
| A：读文件 | 20.7 ms | 206.8 ms |
| A：parse + reduce | 8.8 ms | 88.0 ms |
| **A：全量重放合计** | **29.3 ms**（~34 万事件/s） | **296.2 ms**（~34 万事件/s） |
| B：流式 readline 合计 | 31.5 ms | 280.5 ms（~36 万事件/s） |
| 全量 reduce 状态 JSON 序列化体积 | **35.1 KB** | **270.9 KB** |
| 状态 `JSON.stringify` 耗时 | 0.21 ms | 2.4 ms |

要点：

- **吞吐 ~34 万事件/s，且近似线性**（1 万 → 10 万恰好转 10 倍）；瓶颈在磁盘读（约占 2/3），parse+reduce 仅约 0.9 µs/事件。10 万事件的全量重放（无任何快照）约 0.3 s，已在"崩溃恢复无感"区间。
- **快照体积增长的主要驱动不是黑板，而是调度进度表**：进度表键为 `节点#迭代`，随事件数线性增长（本实验每 ~40 事件一次节点执行 → 10 万事件产生 2500 个进度键）。黑板（worldbook 50 键 + 各 Agent 发言切片）在 1 万→10 万间基本不增长。真实局中黑板会更大（状态表 + worldbook 全文），估计快照典型量级 **数十 KB ~ 数百 KB**，永不到 MB 级。
- **单次快照写入成本可忽略**：序列化 0.2–2.4 ms + 一次同步 append；快照频率的约束不在 CPU，而在**内联条目对 Script 文件的体积膨胀**。

### 2.3 建议值

D30 已定"周期性节点边界 + 局末 + pause 时"三个时机，缺的只是"周期"的数值。基于实测：

**建议：每 10 个节点边界 且 距上次快照 ≥ 500 事件时落一次快照（双条件，先到为准）；局末与 pause 必落。**

推导：

1. **为什么频率可以很低**：无快照全量重放 10 万事件仅 ~0.3 s——MVP 规模（数千至数万事件）下快照对恢复速度是优化而非必需。真正的风险是马拉松局/锦标赛积累数十万事件后恢复变慢（30 万事件 ≈ 1 s），以及无快照时崩溃恢复必须容忍全文件扫描的鲁棒性。500 事件/次的下限保证最坏恢复量 ≈ 500 事件 < 5 ms，余量巨大。
2. **为什么挂钩节点边界而非纯事件数**：快照语义是"reduce 状态检查点"，落在节点边界可保证快照不切割在飞节点（与 D12"恢复点 = 最近完整节点边界"天然对齐），且 D36 孤儿事件判定以节点执行为单位——边界处快照内无歧义。"每 10 个边界"按典型一局每节点 ~30–50 事件估算，恰与 500 事件下限同量级，双条件互为兜底（防止超大节点或超碎节点两种极端）。
3. **体积账**：按每 ~300–500 事件一次快照、快照 ~50–300 KB 计，10 万事件（~55 MB）的局产生 200–300 个快照条目，膨胀约 10–90 MB——占文件 20%–60%。可接受（D11 内联方案成立，不会因快照爆文件），但这是压低频率的真实约束；若未来黑板膨胀到快照 > 1 MB，应优先做进度表裁剪（见未决问题）而非提高频率。

### 2.4 对架构/契约的影响

1. **快照条目（D11）的 schema 按四段组织**：`blackboard`（全量键值）、`agents`（生命周期表）、`progress`（（节点，迭代）→ 状态 + join 等待表，D8）、`ledger`（成本累计切片，D28）——与 §2.3 时序中"快照（reduce 状态检查点：黑板/Agent 生命周期/调度进度）"一致，补成本账本一段（D28 账本是调度状态派生切片，恢复时须随快照还原，否则成本闸在恢复后清零）。
2. **快照触发条件是配置项而非常量**：建议 Bundle/CLI 可配（默认 `every_node_boundaries: 10, min_events: 500`），与 D30 的三个时机并列——锦标赛批量跑局与交互式单局的膨胀容忍度不同。
3. **重放路径的性能结论支持 §4.3 `replay()` 吐事件序列的设计**：34 万事件/s 意味着 reducer 分发到各服务 applyEvent 的纯函数开销完全不是瓶颈，无需为重放引入索引文件或二进制格式——JSONL 文本格式在 10 ⁵ 事件量级无性能借口被替换，导演可读性红利保留。
4. **事件信封体积预算**：本实验信封（id+parent_id+ts+node_exec）约占 100 B/事件；采用推荐的短序号 id（相对 UUID 省 ~54 字符/行）在 10 万事件局省 ~5 MB——问题 1 的推荐在此有量化支撑。
5. **暂停（pause）快照的成本已量化可忽略**（< 3 ms 序列化 + 一次 append），D30 的"pause 时落快照"无性能异议。

## 未决问题

1. **调度进度表的长期裁剪策略**：进度键随事件数线性增长，是快照体积的主要增长源（本实验 10 万事件 → 2500 键）。（节点，迭代）进度是否只需要保留"每节点最新迭代 + 未决 join 等待"，历史已完成迭代可否在快照中裁剪？这涉及 D8/D36 语义（孤儿判定需要最后未完成节点执行标识），属架构裁决，建议提交架构师。
2. **快照条目的完整性校验**：pi 的 CompactionEntry 无自校验（靠 `firstKeptEntryId` 引用完整性）；本系统快照内联在 append-only 流中，尾部半行已有丢弃纪律（§2.3），但快照条目本身是否需要 hash 自校验字段以支撑 `SNAPSHOT_CORRUPT`（§4.3 错误枚举）的判定，架构文档未定义校验算法——留 Schema 阶段。
3. **实测的覆盖边界**：本实测还原了"parse + 纯函数 reduce"的主路径，但未计入 Zod 契约校验开销（恢复路径按 §4 恢复纪律不校验还是校验，架构未明说）；若恢复路径也逐条过 Zod，吞吐预计下降一个量级左右（Zod 官方基准约 10 ⁵ –10 ⁶ ops/s 简单对象），建议 Schema 阶段以真实契约复测一次。
4. **pi 调研文档勘误待落实**：`pi-agent-investigation.md` 的 `uuid`/`parentUuid` 描述对应 pi 会话格式 v1，与当前 v3（`id`/`parentId` + 8 位短 id）不符；该文档非权威故不影响架构，但后续引用者易误读，建议架构师决定是否在原文件加注。
